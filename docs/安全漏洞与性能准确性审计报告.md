## 一、安全漏洞

### 🔴 高危

| # | 漏洞类型 | 位置 | 描述 | 影响 | 修复建议 |
|---|---|---|---|---|---|
| S-1 | **pickle 反序列化** | `src/tools/alpha_bench_tool.py:249` | `pickle.loads(blob)` 加载缓存。注释称"HMAC-authenticated"，但若 HMAC key 泄露或校验逻辑有绕过，攻击者可构造恶意 pickle 实现 RCE。 | 远程代码执行 | 改用 JSON/msgpack 等安全格式；或确保 HMAC key 从环境变量读取且校验在 loads 之前完成 |
| S-2 | **f-string SQL 拼接** | `src/goal/store.py:575`、`src/strategy_store/sqlite_store.py:484`、`src/portfolio/store.py:93`、`src/strategy_discovery/evidence_store.py:288,319,339,352,359` | 多处使用 `f"SELECT * FROM {table}"` 拼接表名。虽然 table 名来自内部常量而非用户输入，但若未来重构引入动态表名，即产生 SQL 注入面。 | 潜在 SQL 注入 | 改用参数化查询或白名单校验表名；添加注释标记"table 必须为内部常量" |
| S-3 | **SSRF 攻击面** | 39 处 HTTP 请求调用（`requests/httpx/urllib/aiohttp`） | 部分 URL 来自用户输入（如 `read_url` 工具、`web_search`）。若未做 URL scheme/host 白名单校验，攻击者可探测内网服务。 | 内网探测/数据泄露 | 统一 URL 校验中间件：仅允许 http/https scheme，禁止 localhost/10.x/172.x/192.168.x/metadata 端点 |

### 🟡 中危

| # | 漏洞类型 | 位置 | 描述 | 修复建议 |
|---|---|---|---|---|
| S-4 | **敏感信息日志泄露** | `src/channels/matrix.py:316,319` | `logger.info("Using password login...")` / `"Logged in using a password"` 虽未直接打印密码，但确认了密码登录路径，缩小攻击者猜测范围。其他 channel 的 `"not configured"` 日志暴露了哪些凭证缺失。 | 降级为 DEBUG；移除凭证存在性确认日志 |
| S-5 | **CORS 宽松配置** | `api_server.py` L173-178 | `allow_origins=_CORS_ORIGINS`、`allow_methods=["*"]`、`allow_headers=["*"]`。若 `_CORS_ORIGINS` 包含通配符或过于宽泛，配合 `allow_credentials=True` 可被利用。 | 审查 `_CORS_ORIGINS` 实际值；生产环境应精确指定域名 |
| S-6 | **全局可变状态** | `logsystem/logger.py:276,286,327`、`analyzer.py:21`、`memory/search_index.py:475`、`shoonya/sdk.py:541` 等 | 多处 `global` 变量作为共享状态。在多进程/fork 场景下可能产生竞态或状态污染。 | 改用线程本地/进程隔离/显式依赖注入 |
| S-7 | **大对象全量读取** | `tools/web_search_tool.py:83,119`、`channels/wecom.py:426`、`trading/tap_forward.py:200` | `.read()` / `.readlines()` 无大小限制。恶意响应可导致 OOM。 | 加 max_size 限制；流式读取 |

## 三、性能分析

### 热点识别

| # | 热点 | 位置 | 影响 | 严重度 | 优化建议 |
|---|---|---|---|---|---|
| P-1 | **emit() 每次 stat** | `logsystem/logger.py:86-89` | 每条日志一次 `os.path.getsize()` syscall。高吞吐下成为瓶颈。 | 🟡 | 用写入计数器替代，仅在接近阈值时 stat |
| P-2 | **RateLimiter bucket 无限增长** | `logsystem/logger.py:196` | 长期运行内存缓慢膨胀。 | 🟡 | 定期 compact 或用环形缓冲区 |
| P-3 | **analyzer 全量文件扫描** | `logsystem/analyzer.py:61-80` | 读取 log_dir 下所有 .log 再过滤。GB 级日志时 O(n) IO + 内存。 | 🟡 | 按文件名 pid/date 预筛 + 流式解析 |
| P-4 | **mask() 30 次正则/日志** | `logsystem/masking.py` | 每条日志对 15 个敏感键 × 2 种模式 = 30 次正则匹配。 | 🟡 | 预编译正则 + 缓存 compiled pattern（P0-2 已改为线性扫描，此条已缓解 ✅） |
| P-5 | **因子 bench 串行** | `factors/bench_runner.py` | 452 因子 × N 股票的 bench 可能很慢。已有 ProcessPoolExecutor 并行化。 | 🟢 | 已优化 |
| P-6 | **web_search 同步阻塞** | `tools/web_search_tool.py:83,119` | `urllib.request.urlopen` 同步调用，在 async handler 中阻塞事件循环。 | 🟡 | 改用 httpx.AsyncClient |

## 八、结论

Vibe-Trading 是一个**功能覆盖最全的开源金融 AI Agent**，在安全门控、前视防护、测试覆盖方面达到业界领先水平。主要风险集中在：

1. **安全**：pickle 反序列化（S-1）和 SSRF（S-3）是需要立即修复的高危项
2. **性能**：logsystem emit stat（P-1）和同步 HTTP（P-6）是可快速优化的热点
3. **准确性**：交易成本建模（A-3）和浮点防护（A-6）是提升回测可信度的关键

**整体安全评分：B+（良好）**——修复 S-1/S-3 后可达 A-。
