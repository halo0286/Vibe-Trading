# A-3 交易成本精细建模：分步实现方案

> **目标**：将 Vibe-Trading 的交易成本建模从当前的"固定滑点 + 简单佣金"提升到"订单簿感知、部分成交、市场冲击动态化"的生产级水平。
> **现状评估**：已有良好基础（见下方），不是从零开始。

---

## 一、现状盘点（已有什么）

### ✅ 已有的成熟组件

| 组件 | 位置 | 能力 | 评级 |
|---|---|---|---|
| **impact.py** | `src/quantlib/impact.py` | fixed_slippage / linear_impact / sqrt_impact / delayed_execution 四种模型 | ★★★★★ |
| **factor_costs.py** | `backtest/factor_costs.py` | ADV 容量上限 + 参与率约束 + 借券成本 + rebalance_cost 整合 | ★★★★★ |
| **ChinaAEngine** | `engines/china_a.py` | 佣金(万2.5+最低5元) + 印花税(万5卖出) + 过户费(万0.1) + 滑点 | ★★★★☆ |
| **CryptoEngine** | `engines/crypto.py` | Maker/Taker 分离费率 + 8h funding fee + 强平费 + 滑点 | ★★★★★ |
| **GlobalEquityEngine** | `engines/global_equity.py` | 美/港/加/印/阿/英/越 各市场独立费率 + 滑点 | ★★★★☆ |
| **Fill 数据结构** | `engines/base.py` | margin + commission + realized_pnl + exit_commission | ★★★★☆ |

### ⚠️ 缺失的能力（A-3 要补的）

| # | 缺失项 | 影响 | 优先级 |
|---|---|---|---|
| G-1 | **部分成交模型** | 大单无法一次填满时，当前要么全填（高估流动性）要么丢弃（低估alpha） | P0 |
| G-2 | **订单簿深度感知** | 滑点是固定 bps，不随盘口深度/买卖价差动态变化 | P1 |
| G-3 | **临时冲击 vs 永久冲击分离** | impact.py 只有总冲击，没有区分"吃掉后恢复"和"吃掉后价格永久移动" | P1 |
| G-4 | **执行算法模拟** | TWAP/VWAP/IS 等算法对冲击的影响未建模（当前假设一次性市价单） | P2 |
| G-5 | **跨市场成本差异统一接口** | 各 Engine 各自实现 calc_commission/apply_slippage，无统一抽象 | P2 |
| G-6 | **成本归因到因子/策略** | factor_costs 有 PeriodCost 但未拆解到"哪些成本来自哪个因子" | P3 |

## 二、分步实现路线图

### Phase 1：部分成交模型（G-1）—— P0，预计 2-3 天

**为什么最先做**：这是回测真实性最大的缺口。当前引擎假设"目标权重 = 实际持仓"，忽略了大单在有限流动性下的渐进建仓过程。

#### Step 1.1：定义 PartialFill 数据模型

```python
# backtest/engines/partial_fill.py (新文件)

@dataclass(frozen=True)
class PartialFillSchedule:
    """描述一笔订单在多根 bar 内的渐进成交计划。"""
    total_shares: float          # 目标总股数
    fill_schedule: np.ndarray    # 每根 bar 的成交量 (shares)
    fill_prices: np.ndarray      # 每根 bar 的成交价 (含冲击)
    unfilled_shares: float       # 最终未成交部分
    participation_rates: np.ndarray  # 每根 bar 占 ADV 的比例
    
    @property
    def avg_fill_price(self) -> float: ...
    
    @property 
    def total_cost(self) -> float: ...
```

#### Step 1.2：实现参与率约束下的渐进成交

```python
def build_partial_fill_schedule(
    target_shares: float,
    adv_per_bar: float,
    max_participation: float = 0.1,   # 最多占 ADV 的 10%
    max_bars: int = 5,                # 最多跨 5 根 bar
    impact_fn: Callable = sqrt_impact,
    volatility: float | None = None,
) -> PartialFillSchedule:
    """将一笔大单拆分为多根 bar 的渐进成交计划。
    
    每根 bar 成交量 = min(剩余量, ADV × max_participation)
    每根 bar 成交价 = 参考价 + impact(累计已成交量 / ADV)
    """
```

#### Step 1.3：集成到 Engine 基类

- 在 `base.py` 的 `_execute_rebalance` 中，当 `abs(target - current) > threshold` 时调用 `build_partial_fill_schedule`
- 未成交部分记入 `PendingOrder`，下一根 bar 继续尝试
- 新增配置项 `partial_fill_enabled: bool = True`、`max_participation: float = 0.1`

#### Step 1.4：测试

- 单元测试：验证不同 ADV/参与率下的成交分布
- 回归测试：对比开启/关闭部分成交的回测 Sharpe 差异（预期 Sharpe 下降）
- 边界测试：ADV=0、target=0、max_bars=1

### Phase 2：订单簿深度感知 + 冲击分离（G-2 + G-3）—— P1，预计 3-4 天

#### Step 2.1：扩展 impact.py 增加临时/永久冲击分离

```python
# src/quantlib/impact.py 新增

def decomposed_impact(
    price: float,
    order_size: float,
    adv: float,
    sigma: float,
    direction: int,
    *,
    permanent_coeff: float = 0.1,    # 永久冲击系数
    temporary_coeff: float = 0.5,    # 临时冲击系数  
    temporary_decay: float = 0.5,    # 临时冲击衰减指数 (bar^-decay)
) -> tuple[float, float]:
    """返回 (temporary_impact, permanent_impact)。
    
    permanent: 价格永久移动，后续 bar 的参考价都偏移
    temporary: 仅当根 bar 的额外成本，下一根 bar 恢复
    """
```

#### Step 2.2：盘口深度代理模型

由于回测通常没有 Level-2 数据，用 OHLCV 构造盘口深度代理：

```python
def estimate_book_depth(
    high: float, low: float, close: float, volume: float,
    tick_size: float,
) -> float:
    """从 OHLCV 估算有效盘口深度（shares per tick）。
    
    原理：日内价格范围 / tick_size ≈ 触及的价格档位数量
    每档平均深度 ≈ volume / 档位数
    """
```

#### Step 2.3：动态滑点替代固定 bps

```python
def dynamic_slippage(
    order_size: float,
    estimated_depth: float,
    spread_bps: float,
) -> float:
    """基于盘口深度的动态滑点。
    
    小单 (< depth): ~0.5 × spread
    大单 (> depth): spread + impact(order_size / depth)
    """
```

#### Step 2.4：集成到各 Engine

- ChinaAEngine：用 tick_size=0.01 估算深度
- CryptoEngine：可用真实 L2 数据（OKX/Binance API 提供）
- GlobalEquityEngine：按市场设定不同的 depth 估算参数

### Phase 3：执行算法模拟（G-4）—— P2，预计 2-3 天

#### Step 3.1：定义执行算法接口

```python
class ExecutionAlgorithm(ABC):
    @abstractmethod
    def schedule(self, total_shares, bars, adv_series) -> np.ndarray:
        """返回每根 bar 的计划成交量。"""

class TWAP(ExecutionAlgorithm):
    """时间加权：均匀分配到 N 根 bar。"""

class VWAP(ExecutionAlgorithm):
    """成交量加权：按历史 ADV 分布分配。"""

class ImplementationShortfall(ExecutionAlgorithm):
    """最小化决策价与成交价的偏差：前期激进后期保守。"""
```

#### Step 3.2：算法选择器

```python
def select_algorithm(
    order_size: float, adv: float, urgency: str = "normal"
) -> ExecutionAlgorithm:
    """根据订单大小和紧急程度自动选择算法。
    
    < 1% ADV → TWAP
    1-5% ADV → VWAP  
    > 5% ADV or urgency="high" → IS
    """
```

### Phase 4：统一成本接口 + 因子归因（G-5 + G-6）—— P2-P3，预计 2 天

#### Step 4.1：统一 CostModel 抽象

```python
class CostModel(ABC):
    """所有 Engine 共享的成本计算接口。"""
    
    @abstractmethod
    def calc_commission(self, notional, direction, is_open) -> float: ...
    
    @abstractmethod
    def calc_slippage(self, price, order_size, adv, direction) -> float: ...
    
    @abstractmethod
    def calc_market_impact(self, price, order_size, adv, sigma, direction) -> float: ...
    
    def total_cost(self, ...) -> CostBreakdown:
        """返回结构化成本拆解。"""
```

#### Step 4.2：CostBreakdown 归因

```python
@dataclass
class CostBreakdown:
    commission: float       # 佣金/税费

    borrow_cost: float      # 借券费
    opportunity_cost: float # 部分成交的机会成本
    
    @property
    def total(self) -> float: ...
```

## 三、实施顺序与依赖关系

```
Phase 1 (部分成交) ──→ Phase 2 (冲击分离+盘口) ──→ Phase 3 (执行算法)
                                                      ↓
                                              Phase 4 (统一接口+归因)
```

- Phase 1 是基础，Phase 2/3 依赖它
- Phase 4 可以在任何阶段并行推进（重构现有代码到统一接口）
- 每个 Phase 完成后跑全量测试确认无回归

## 五、风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 部分成交导致回测 Sharpe 大幅下降，用户不满 | 高 | 中 | 默认关闭，opt-in 启用；提供"简单模式"vs"精细模式"切换 |
| 盘口深度估算不准 | 中 | 中 | 提供校准工具；允许用户传入真实 L2 数据覆盖估算 |
| 统一接口重构破坏现有 Engine | 中 | 高 | 渐进式迁移：先建新接口，旧 Engine 适配层保留 2 个版本 |
| 性能退化（部分成交需多 bar 循环） | 低 | 中 | numpy 向量化；缓存 ADV；提前终止条件 |

## 六、建议启动顺序

**推荐先做 Phase 1（部分成交）**，因为：
1. 它是回测真实性最大的缺口
2. 不依赖其他 Phase
3. 改动集中在 `engines/base.py` + 新文件，不影响现有 Engine 的具体实现
4. 可以立即验证效果（对比 Sharpe 变化）
